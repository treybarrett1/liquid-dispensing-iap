# IAP M3 - Critique of the AI's First Domain Model

## Personal Written Critique

The AI’s first domain model captured the main parts of my dispenser, but it included more structure than I think this project needs. It used 13 classes and three enumerations. My revised model uses seven classes. My goal was not simply to reduce the number of boxes, but to make each object’s purpose and lifetime clearer.

One example of over-modelling was separating Dispenser, FillRequest, BottlePreparation, and DispenseRun. These objects describe different stages of one interaction, and the target volume appeared in both the request and run. I combined the current interaction into FillSession, which holds the target, bottle confirmation, tare, and operating state. My requirements do not call for queued requests or independently stored bottle-preparation records, so those separate objects added complexity without a clear benefit.

The biggest weakness was ownership of manual additions. The AI made DispenseRun the composite owner of ManualAddition, while RunOutcome referenced those additions for retained history. That left an important question unanswered: what happens to the addition details when the current run object is discarded? In my model, the durable RunRecord owns its additions, so their lifetime matches the saved result.

The AI also separated PendingRunMarker from RunOutcome, repeating the run identifier and target. I represented these as states of one RunRecord. A record begins as Pending and later becomes Confirmed, Cancelled, or Failed. After an interruption, recovery updates the same record instead of creating a second identity. This makes duplicate prevention easier to explain, although reliable storage still requires implementation and testing.
One relationship the AI supplied without a clear requirement was linking every run to a fixed calibration-version object. Keeping calibration unchanged during a fill is sensible, but M2 does not require a historical calibration-version registry. My model therefore uses validated calibration values for the active session without assuming that additional history structure.

The AI was right to distinguish bottle capacity from bottle detection, calibration from sensor readings, and completed additions from successfully measured additions. It also correctly treated interrupted measurements as checkpoints rather than final results. I retained those distinctions.
Overall, the AI draft helped identify the domain concepts, but I would not accept its structure unchanged. My revised model makes temporary interaction state and durable records easier to distinguish, while keeping the relationships tied to the M2 requirements. Neither model proves that shutdown timing, storage recovery, or physical dispensing will work; those still need testing.

## Evidence and conclusion

The [unchanged first draft](ai/M3_DOMAIN_FIRST_DRAFT.md) was generated from the actual [M2 requirements](M2_REQUIREMENTS.md), saved, hashed, and committed as `63ed81f` before the [revised model](M3_DOMAIN_MODEL.md) was created. The [exact prompt](ai/M3_DOMAIN_PROMPT.txt) and [provenance](ai/M3_DOMAIN_CONTEXT.md) make the comparison reproducible. Both the revision and this critique received Codex assistance.

The first draft is strong on dispensing rules but less clear about object lifetime. It has 13 ordinary classes and three enumerations. The revision has seven classes and documents enums as attribute types. The reduction is not the goal by itself: the revised model separates transient session data from retained results, removes relationships that would force completed records to depend on temporary objects, and makes the pending-to-terminal record transition explicit. The AI draft would be usable after those changes; rejecting all of it would discard several correct domain distinctions.

The AI did **not** add User, Role, Permission, a generic Settings entity, or an AuditLog. The assignment warns about that pattern, but it did not occur here. This critique evaluates the actual response rather than attributing stereotypical mistakes to it.

US-01/02/04 require those values and checks, not separately identifiable requests/preparations with their own retained lifecycles. Merging them removes duplicate target state and avoids a join through a discarded request to find the tare. Splitting them could become worthwhile if requests were queued or reused, but M2 asks for neither. |
| O-02: a gesture is promoted to a lasting relationship | `ManualAdditionGesture "1" --> "0..1" ManualAddition` gives every issued addition exactly one associated gesture; `Dispenser` separately owns the current gesture reference. | `FillSession.tapState` plus the explicit consume/cancel/no-queue rules represent US-06's temporary interaction. Only the issued `ManualAddition` value is retained. A saved addition does not need a surviving touch object. This preserves one action per completed tap while separating UI event lifetime from calibration evidence. |
| O-03: a collection of observations is not required | `DispenseRun "1" *-- "0..*" VolumeMeasurement`, with each measurement linked to a `SensorFrame`, introduces an observation collection beyond the final/addition measurements M2 requests. | Keep the latest `SensorFrame` transient, calculate live volume, and retain only the run's result/checkpoint and required addition increases. The AI explicitly says these observations need not all be persisted, so it did not demand an unlimited database. Even as a runtime conceptual collection, however, the extra objects do not serve a stated history requirement and invite unnecessary storage/lifetime decisions. |
| O-04: marker and outcome duplicate one run's identity | `PendingRunMarker` and `RunOutcome` both repeat run ID and target and each associates back to `DispenseRun`. `LocalHistory` has separate owned collections for them. | One `RunRecord` has Pending or terminal status. ## Where it under-modelled or left an important gap

| Finding | Evidence and consequence | Revision / remaining validation |
| --- | --- | --- |
| U-01: retained addition ownership is ambiguous | `DispenseRun "1" *-- "0..*" ManualAddition` makes the run the composite owner, but `RunOutcome "0..1" --> "0..*" ManualAddition` merely references those same parts. Only the outcome is explicitly retained by `LocalHistory`. If the runtime run is disposed, composition leaves the intended survival of its additions unclear. | `RunRecord "1" *-- "0..*" ManualAddition` gives results one durable owner. Closing the session does not dispose of the record; evicting the retained record disposes of its addition values. This is a lifecycle clarification, not a claim that a Mermaid arrow alone would cause a particular database deletion. |
| U-02: a saved outcome appears to require a live run | `DispenseRun "1" --> "0..1" RunOutcome` implies exactly one run for each outcome, while the coordinator has only one current run. The draft does not say whether old run objects are retained along with the latest 50 outcomes. | `FillSession "0..1" --> "0..1" RunRecord` explicitly allows retained records without live sessions. NFR-03 needs history after reboot, when no old session object exists. |
| U-03: pending evidence lacks addition state | `PendingRunMarker` contains run ID, target, time, and optional measured checkpoint, but no addition entries/counts. The draft itself flags that more checkpoint data may be needed. | The pending `RunRecord` can preserve acknowledged addition values and its checkpoint measurement kind using the same schema as the eventual outcome. Exact checkpoint frequency and storage atomicity remain open; the revision does not promise recovery of unsaved latest readings. This turns the AI's useful question into an explicit data/lifecycle decision. |
| U-04: counts can disagree | Both `DispenseRun.manualAdditionCount` and `RunOutcome.manualAdditionCount` are stored beside a collection of `ManualAddition.completed` flags. No structural rule defines which is authoritative. | `RunRecord.completedAdditionCount()` is derived from completed addition entries. Allocation must itself be durable. The invariant is 50 terminal records plus at most one pending record; capacity 51 by itself is insufficient. |

## Relationships the model supplied without a requirement basis

The draft says `DispenseRun "0..*" --> "1" CalibrationProfile : fixed calibration version`, and gives each profile a `version`. M2 US-03 requires valid calibration/provenance, but it does not require a historical calibration-version entity associated with every retained run. Keeping calibration stable during an authorized run is sensible; assuming the domain must retain a version-linked profile history is an additional design choice. The revision binds immutable calibration values to a live session and keeps provenance in the configuration. A future calibration-comparison feature could justify retaining a version/snapshot per record, but that must be an explicit extension. The AI listed fixed calibration as an assumption, which is good disclosure; it did not prove M2 requires that association or a version table.

The one-to-one authorization link `DispenseRun "0..1" --> "1" FillRequest` is also a proposed lifecycle policy: it says every run needs a distinct request object. M2 US-05/08 requires renewed readiness and confirmation, not a separately identifiable request entity. The revised session lifecycle enforces renewed confirmation directly. It preserves the safety rule while declining to treat an unrequested request-object identity as a domain requirement.

Other links have a clear basis and should not be called guesses: a run can have many additions (US-06/07); bottle options have usable capacity (US-02); a pending marker is needed before pumping (US-08); and history needs bounded retention (NFR-03). The revision changes the representation of some of these facts without rejecting the facts themselves.

## Where the AI was right

1. **A dispense run is the central unit of identity.** Target, additions, cancellation/failure, and recovery must be correlated. The revision preserves `runId` as the unique key and does not invent an account model.
2. **Bottle capacity and bottle preparation are different concepts.** A break beam cannot establish capacity or emptiness. The revision retains `BottleSpec` and explicit confirmation/tare fields, even though preparation becomes part of the session.
3. **Calibration and sensor frames are distinct.** Fixed conversion/limit values should not be mixed with changing observations. The revision keeps both and preserves explicit validity/freshness handling.
4. **Additions are bounded actions with their own results.** `ManualAddition` correctly separates completion from whether an increase can be measured. The revision retains that distinction, with a durable owner and a sequence local to the run.
5. **Incomplete recovery data must not look final.** The draft correctly describes pending measurements as checkpoints and interrupted runs as failed with a reason. The revision makes the distinction an explicit `MeasurementKind` instead of relying only on prose.
6. **Timing and fluid behavior are not established by a class diagram.** The AI maps NFR-01/02 to implementation verification and separates an off command from physical cessation of flow. Those limits remain in the revised model.

## Why the revised structure is preferable for this milestone

The revised model makes three questions answerable directly: what exists only while someone is operating the device (`FillSession`, latest `SensorFrame`), what defines a configured decision (`BottleSpec`, `Calibration`), and what must survive a reboot (`RunRecord` with addition values in `LocalHistory`). Durable state no longer depends on preserving discarded gestures, a request/preparation object chain, or a runtime run that owns the outcome's children.

This simplification has limits. Class multiplicities cannot enforce touch-event timing, atomic storage, or actual pump shutdown. The accompanying invariants and M2 acceptance tests supply those obligations. A single logical record still needs a crash-safe backend, oldest-first retention, and reliable recovery under real power interruptions. The resulting model is a justified design proposal, not implemented firmware or physical validation.
